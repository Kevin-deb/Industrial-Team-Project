# Requirements Traceability and Scope Decisions

This document links the supplied requirements to module owners, delivery iterations, API boundaries and acceptance checks. A visible preview or reserved table does not mean the business feature is implemented. Iteration 0 contains an installable Windows desktop shell, Chinese/English switching, synthetic read views and future-feature placeholders; subsequent iterations implement the clinical workflows.

Updated v3 architecture decks in `docs/presentations/` incorporate U1 and the current five-person iteration plan; they are design outputs, not additional customer requirements.

The source files remain in their supplied locations outside the software repository. The requirement IDs below are assigned for this implementation plan, not IDs from the original documents. Iteration estimates, technology, member labels and proposed state machines are engineering decisions.

Status vocabulary: **Preview** means a working synthetic read/UI demonstration; **Reserved** means a schema/contract/placeholder for later development; **External** means owned by another platform subsystem; **Optional** means an extension after core acceptance. API paths marked **planned** are future interface proposals; the current write guard returns `501 FEATURE_NOT_IMPLEMENTED`.

## Source differences and working decisions

1. **Remote consultation scope.** R1 and R3 explicitly require it for the doctor. R2's final configuration section includes it among switchable modules. Treat it as a core doctor capability delivered in I3, with an institution-level enable/disable option. Peer community remains the clearly optional extension.
2. **Recording defaults.** R1 says recording is supported; R3 s5 describes automatic recording. A1 s4 says recording follows policy. Implement recording capability after consent/defaults, retention and access decisions. Automatically saving consultation text does not imply unconditional recording of every video call.
3. **Security and preservation language.** R3 s10–11 uses absolute language about immutability, loss and confidentiality. Convert that intent into access controls, append-only audit behavior, protected storage, backup/restore and agreed measurable targets. Do not promise an absolute result the system cannot prove.
4. **More detailed PPT fields.** Admission dates, treatment stages/plans, keyword/date history search, real-time order validation and heart rate appear explicitly in R3. Preserve them in the backlog, while recognizing that R1 is less specific. The initial DTOs and preview filters do not yet implement every one of these fields.
5. **Reports and clinical responsibility.** The sources request generated expert reports but do not require AI diagnosis. Compiling structured findings into a draft, followed by doctor confirmation, is the proposed implementation rule from A1 s5 and s9.
6. **Cross-system permission responsibilities.** R2 assigns patient authorization to the personal app and role configuration to administrators. This team implements enforcement/integration seams in its API. A successful doctor login cannot substitute for scoped patient permission.
7. **Unspecified conditions.** Duration, member identities, provider budgets, deployment host, concurrency/latency targets, retention, recovery objectives and external data standards are not specified. The plan labels estimates and schedules decisions before dependent work.

## Core acceptance scenarios

The following scenarios link several requirements and prevent isolated module success from masking integration failures:

- **Authorized visit:** scoped doctor finds patient → accepts encounter → messages save → draft submitted → authorized senior reviews → approved record archives. Check profile versions and independent order history. Covers AUTH-02, PAT-01/02, ENC-01/04, EMR-01/02 and ORD-01.
- **Temporary expert access:** invite scoped expert → view permitted material → confirm report → complete task or expire/revoke grant → deny subsequent chart/file/export/live access. Covers AUTH-03/04 and CON-01/02/03.
- **Continuing care:** receive a validated reading → show provenance and trend → revise plan after assessment → enqueue reminder → retry provider failure without duplicate delivery. Covers HLT-01/02/03, PLT-02 and NFR-02.
- **Recovery:** preserve a completed visit, archive, order versions, grants and jobs in a backup; restore and verify relationships and permitted access. Covers AUD-01, NFR-02 and NFR-03.
- **Optional isolation:** post only manually edited content → receive community interaction → disable module → receive no social notification; patient and consultation workflows remain usable. Covers SOC-01–05.

Only framework desktop installation/startup, bilingual UI, read/navigation and placeholder checks apply to the current release. Each clinical scenario becomes an acceptance gate in the iteration that enables its dependent functions.
