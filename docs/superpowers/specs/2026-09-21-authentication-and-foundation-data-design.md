# CareLink 登录、授权与基础数据库设计

日期：2026-09-21  
范围：A 登录与权限基础、B/E 既有接口联动、合成演示数据库初始化

## 1. 目标与边界

本次将当前“启动时固定演示医生”改为数据库驱动的真实本地登录会话，并为 5 名医生、10 名患者建立一致的基础数据和明确的医生—患者访问关系。登录成功只证明用户身份，不自动授予所有患者数据访问权；每一次患者搜索、详情读取和业务写入仍需通过患者范围授权。

本地版本提供账号或邮箱加密码登录、退出登录、会话保持、会话失效、当前医生信息和前端路由保护。短信及人脸验证继续通过 `IdentityProvider` 端口保留，不在没有真实供应商的情况下伪造成功流程。管理员和专家角色保留并提供可测试的权限策略，但不在本次扩展为完整管理后台。

所有人员、患者和临床资料均为合成演示数据。同行社区继续只引用医生身份，不读取或自动发布患者临床数据。

## 2. 选择的认证方案

采用服务端不透明会话令牌：

- 用户以账号或邮箱和密码登录。
- 密码使用 Node `crypto.scrypt`、独立随机盐和恒定时间比较；数据库不保存明文密码。
- 登录成功后生成高熵随机令牌，仅把令牌摘要存入 `user_sessions`。
- 桌面渲染器只持有当前会话令牌；私有 `carelink://` 协议把授权头转发给内嵌 Fastify，不允许渲染器指定 `actorId`。
- 会话具有创建时间、最近使用时间、固定失效时间和撤销时间。退出登录立即撤销当前会话。
- 应用重启后可恢复未过期、未撤销的会话；切换账号或退出时清除前端查询缓存、患者选择和实时订阅。

不采用 JWT。当前是单机 SQLite 和内嵌 API，服务端会话更容易即时撤销、审计和控制账号切换，也不会把角色及患者范围长期复制到客户端令牌中。

## 3. 数据模型

### 3.1 账号与人员

- `users`：登录账号，包含 `id`、`username`、规范化邮箱、状态、密码摘要、密码盐、密码算法参数、失败次数、锁定时间、创建及更新时间。
- `identities`：沿用现有医生业务身份；新增账号通过 `users.identity_id` 与之关联。
- `doctors`：医生档案扩展，包含执业编号、科室、职称、医院、专业方向、联系电话和启用状态；显示字段仍可从现有 `identities` 兼容读取。
- `roles`、`identity_roles`、`role_permissions`：沿用并扩展为 `doctor`、`expert`、`admin`。管理员管理账号不等于自动拥有所有病历读取权。
- `user_sessions`：令牌摘要、用户、创建/最后使用/失效/撤销时间、客户端类型。任何会话验证都从这里解析可信 `actorId`。

### 3.2 医生—患者范围

沿用并演进现有 `access_grants`，作为 `doctor_patient_access` 的实际授权来源：

- 每名患者有一名主要负责医生，另可有协作医生或限时专家。
- 授权记录包含范围、任务、失效和撤销字段。
- 患者列表、搜索和详情对无权限医生表现为不存在，不泄露姓名、编号或数量。
- 临时专家访问在任务关闭、到期或撤销后立即失效。
- 授权变更和拒绝访问均写入元数据审计，不记录密码、令牌或完整临床正文。

## 4. 初始化数据

初始化 5 名医生和 10 名患者，使用稳定 ID，保证不同模块引用一致：

- 医生覆盖全科、心血管、内分泌、呼吸和专家/管理协作场景。
- 10 名患者覆盖高血压、糖尿病、冠心病、慢阻肺和康复管理等合成场景。
- 每位患者绑定一名主要医生；部分患者增加一名协作医生；至少保留多组明确不可访问组合用于权限测试。
- 患者、问诊、病历、健康观测、计划、提醒和审计使用同一患者/医生 ID。
- 社区初始化 5 名医生的资料、圈子、帖子、评论、通知和私信，不创建患者社区身份，也不把临床事件订阅到社区。

种子数据必须幂等：已有数据库升级后补齐缺失账号和关系，不重复创建业务记录；全新数据库可一次得到完整演示环境。

演示账号会在登录页以“演示账号提示”呈现，密码来自本地演示配置，不把密码写进日志、API 响应或生产构建说明。首次启动可使用固定的合成演示密码，后续可替换为配置或真实身份供应商。

## 5. API 与请求身份

新增接口：

- `POST /api/v1/auth/login`：账号/邮箱与密码换取会话。
- `POST /api/v1/auth/logout`：撤销当前会话。
- `GET /api/v1/session`：返回当前医生、角色、会话失效时间、演示模式和免责声明。

除健康检查、登录和静态资源外，所有 `/api/v1` 业务路由都要求有效会话。请求钩子解析令牌并在请求对象中保存认证上下文；患者、临床、健康、社区、审计和 WebSocket 都从该上下文取得 `actorId`，不再从 `createApp({ identity })` 的全局固定值取得身份。

测试仍可通过专用测试会话辅助方法创建身份上下文，但生产/桌面运行路径不接受调用方直接传入医生 ID。

常见失败响应保持统一：凭据错误为 `401 INVALID_CREDENTIALS`，会话缺失或失效为 `401 AUTHENTICATION_REQUIRED`，账号停用为 `403 ACCOUNT_DISABLED`，权限范围不足在患者资源上返回 `404 NOT_FOUND`，避免资源枚举。

## 6. 桌面和前端流程

- 未登录时只显示中英文登录页；不能通过地址直接进入工作台。
- 登录成功后载入当前医生、角色和其可见患者；顶部及设置页显示同一身份。
- 退出登录后返回登录页，并清空本账号的客户端状态与实时连接。
- 会话过期时任何 API 的 `401` 统一触发退出状态；不会继续展示上一个医生缓存的数据。
- 社区 WebSocket 订阅当前会话医生；账号切换时先释放旧订阅，再建立新订阅。
- 登录页沿用现有 CareLink 视觉和中英文切换，不新增夸张字体或无意义大面积留白。

## 7. 安全与审计

- 登录错误使用一致文案，避免暴露账号是否存在。
- 失败尝试达到阈值后短时锁定，成功登录清零失败计数。
- 所有令牌随机生成、只保存摘要、响应禁止缓存；密码和令牌不进入日志。
- 登录成功/失败、退出、会话过期、患者访问成功/拒绝和授权变更写入审计事件。
- 数据库启用外键、WAL 和现有迁移历史校验；新增迁移只向前升级，不重写历史迁移。

## 8. 验收与测试

最低验收覆盖：

1. 正确账号或邮箱可登录，错误密码、停用账号和锁定账号均失败。
2. 数据库中不存在明文密码或明文会话令牌；退出和过期会话无法重放。
3. 未登录无法进入前端业务路由，也无法调用业务 API 或建立社区实时连接。
4. 应用重启后有效会话恢复；退出后重启仍保持退出。
5. 两名医生登录后看到不同的患者集合；无权限患者不出现在搜索结果，直接访问详情也返回不存在。
6. 临时专家授权在到期、撤销或任务结束后立即失效。
7. 切换账号后旧患者缓存、社区未读数和 WebSocket 事件不会串到新账号。
8. 初始化数据库严格包含 5 名医生、10 名患者及预期访问矩阵，各模块外键引用一致。
9. 中英文登录、失效提示和退出流程均可操作。
10. 既有 B/E 患者、健康、社区和审计集成测试在改为会话身份后继续通过。

## 9. 非目标

本次不实现真实短信网关、人脸识别、云端统一身份、患者端授权 UI、完整管理员控制台、生产密钥托管或生产级合规认证。对应端口和数据关系保留，后续接入时不需要改写 B/E 业务接口。
